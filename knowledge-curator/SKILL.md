# 知识库问答与沉淀

把当前活动目录视为知识库根目录。先用本地材料回答；只有本地证据不足、过时或冲突时才研究外部来源。回答问题与沉淀知识是两个独立决定：必须回答问题，但只保存值得长期复用且证据可靠的增量信息。

## 核心流程

### 1. 确定范围

1. 以当前活动目录为默认知识库根目录；用户指定子目录或文件时缩小范围。
2. 运行 `pwd`、`rg --files`，识别 Markdown、纯文本、PDF、Office 文档、索引/MOC、目录说明和命名惯例。
3. 排除 `.git/`、构建产物、依赖目录、缓存和临时文件。不要把 Skill 自身说明当成领域知识，除非问题就是关于该 Skill。
4. 仅在无法可靠确定知识库根目录且不同选择会改变写入位置时询问用户。

### 2. 先检索本地知识

先运行无依赖检索脚本，再定向读取候选文件：

```bash
python3 <skill-dir>/scripts/search_knowledge_base.py "用户问题" --root .
```

- 若 `<skill-dir>` 位于知识库根目录内，用 `--exclude '<相对Skill目录>/**'` 排除 Skill 自身。脚本退出码 `0` 表示有候选，`1` 表示没有达到相关度阈值的候选，`2` 表示参数或路径错误。
- 阅读排名靠前的 3–8 个候选片段及其上下文，不要只依据命中行作答。
- 用 `rg -n` 补查同义词、缩写、英文名、旧称和关键实体。
- 对 PDF、DOCX、PPTX、XLSX 等二进制候选使用对应的格式工具读取；不要用 `strings` 代替可靠解析。
- 记录能直接支持结论的文件、章节和行号，并检查材料日期。

出现以下任一情况，判定本地信息不足：

- 只有关键词提及，没有直接回答问题的内容；
- 关键结论缺少依据，或重要维度明显缺失；
- 来源互相冲突且本地材料无法消解；
- 问题涉及“最新”、当前版本、价格、政策、接口或其他时效信息，而本地材料可能过期；
- 检索脚本无高相关候选，定向同义词搜索也没有补充。

### 3. 用证据回答

- 本地材料足够时，直接回答，不为“显得完整”而额外联网。
- 先给结论，再给依据、边界条件和可验证路径。
- 区分本地文件中的事实、外部来源中的事实、推断和建议。
- 引用本地文件时给出可定位的路径与章节或行号；不要声称未读文件支持结论。
- 材料冲突时分别陈述，不强行合并；说明哪项证据更可靠及原因。

### 4. 必要时研究外部来源

本地信息不足时再联网。技术和学术问题优先级如下：

1. 标准、官方文档、官方数据和原始论文；
2. 作者或机构的一手材料；
3. 高质量综述或可信二手资料。

对论文优先查原文、摘要、方法、实验和限制，而不是只看搜索摘要。对时效性问题核对发布日期、事件日期和版本。回答中为外部事实提供链接，并明确哪些结论来自外部补全。

不要把搜索摘要、单一博客观点或尚未核验的推测写成确定事实。无法核验时明确说明缺口。

### 5. 独立决定是否沉淀

仅当新信息同时满足以下条件时写回知识库：

- 超出当前一次性回答，未来很可能复用；
- 能补足现有知识缺口，而不是重复已有内容；
- 有可追溯的可靠来源；
- 结论稳定，或能够用日期/版本清楚限定；
- 不包含凭据、隐私、受限内容或大段受版权保护的原文。

以下情况默认不写入：一次性操作结果、未经核验的主张、纯搜索过程、很快失效且无历史价值的数据、与知识库主题无关的内容、现有文件已完整覆盖的内容。

一旦决定写入，必须先完整读取 [references/filing-policy.md](references/filing-policy.md)，再选择目标并编辑。

### 6. 选择目标并安全整合

遵循“现有文件优先、宽主题优先、原子知识点作为章节”的顺序：

1. 查找是否已有能容纳该知识的主题文件或近义章节。
2. 从目录名、索引/MOC 和实际内容判断目录职责，选择能覆盖该主题的最深层现有目录；不要只凭目录名猜测。
3. 检查候选目录的文件名、索引/MOC 和至少两个最相近的同级文件；同级只有一个文件时检查该文件。
4. 优先把新知识合并进现有主题文件的合适章节，避免在文末机械追加重复段落。
5. 只有没有合理宿主文件、知识值得长期保留且主题足够宽时才新建文件。只有新分类能够容纳多个文件且符合现有目录层级时才新建目录；不要为单个知识点创建一层目录。
6. 用“可容纳多个相关知识点的最小稳定主题”命名文件。不要用单个模型、术语或孤立事实直接命名：
   - BERT → `自然语言处理.md` 或现有分类下的 `预训练语言模型.md`，不要新建 `BERT.md`；
   - 某个注意力变体 → 现有的 `注意力机制.md`；
   - 某条 Python 小技巧 → 现有的 `Python.md` 或更合适的工程主题文件。
7. 新建文件时，只要同目录存在其他知识文件，就必须向其格式看齐：扩展名、frontmatter 字段及顺序、标题层级、段落组织、列表符号、链接语法、标签、引用/来源格式、语言和文件名风格均以同级文件为准。
8. 同级格式不一致时，以主题最接近的文件为第一参考，以多数惯例为第二参考；不要拼出一种目录中不存在的混合格式。
9. 只有空目录或无任何可参考知识文件时，才使用简洁 Markdown：一级标题、短段落、必要的小节和“来源”部分。
10. 保留原有 frontmatter、人工观点、链接和章节顺序。只做与本问题相关的最小改动。
11. 如果该目录一贯维护索引、MOC 或双向链接，同步更新；否则不要凭空引入新体系。

### 7. 写后验证并交付

编辑后必须：

- 重读修改段落及前后文，确认语义连贯、无重复、标题位置正确；
- 用 `rg` 检查重复知识点、目标文件名和内部链接；
- 检查外部来源链接、论文标识、日期/版本限定；
- 在 Git 仓库中运行 `git diff --check` 并审阅仅与本次任务相关的 diff；
- 不覆盖或整理用户已有的无关改动。

最终回答必须包含：

- 对用户问题的直接答案；
- 主要依据及仍不确定的部分；
- 是否使用了外部信息；
- 若写回：修改或新建的文件路径、归档理由和新增来源；
- 若未写回：一句话说明未达到哪项沉淀条件。

## 完成标准

- 已先检索本地材料，并能展示可复核的本地依据或明确的未命中结果；
- 外部研究只补足真实缺口，且来源层级与问题风险匹配；
- 答案中的事实、推断和建议可区分；
- 写回内容可追溯、不重复、位置合理；
- 新文件主题粒度足够宽，并严格继承同目录格式；
- 所有改动通过定向复读、链接/重复检查和 diff 检查。
