# 技术笔记元数据整理评测规则

不要把执行者自己声称“已校验”当作通过证据。评分者应独立检查输入、输出与报告。

所有评测的计划、说明、异常和报告必须使用简体中文；路径、命令、代码、YAML 键名和原始属性值不要求翻译。出现少量必要的技术标识符不算违反中文输出要求。

每次评测开始前，把 `evals/files/` 中列出的输入复制到该次评测的独立工作目录，并记录原始测试文件与工作副本的 SHA-256。执行者只能修改工作副本或输出目录；评测结束后，原始测试文件的哈希必须保持不变，避免污染基线、并行运行或后续迭代。

## 评测 1

1. 确认原始测试文件哈希未变，并将输出中的两个同名 Markdown 文件与 `expected/technical-vault/` 下的标准答案文件做逐字节比较。
2. 独立提取工作副本输入与输出的 frontmatter 结束标记，比较结束标记之后的 SHA-256；两份正文哈希都必须保持不变。
3. 用拒绝重复键的 YAML 解析方式读取输出，核对 `tags` 的值与类型。
4. 确认输出目录没有出现范围外的修改文件。
5. 对输出再计算一次相同映射；预期修改数为 0。仅有报告中的“幂等通过”字样不计分。

## 评测 2

1. 执行前后分别计算全部输入文件的 SHA-256；任何变化都直接判定只读要求失败。
2. 重复键必须从 YAML 词法/事件流或启用重复键拒绝模式的解析结果中确认，不能使用普通映射加载后的结果。
3. 在 Obsidian 模式下，`dot-end.md` 的 `...` 不计作 frontmatter 结束边界。
4. 对照每条 expectation 检查报告中的文件名、问题类型和边界说明；模糊声称“有问题”不计分。
5. 报告必须使用简体中文，同时保持路径、键名和原始属性值准确。

## 评测 3

1. 执行前后比较全部输入文件哈希，确认没有写入。
2. 评分报告是否同时给出值出现次数、受影响文件数、完整旧值 → 新值候选映射及待用户决定项。
3. 若输出未经用户确认就选定语言、改文件或扩展到正文/aliases，判定失败。
4. 方案和待确认问题必须使用简体中文。
