# 技术笔记元数据整理

安全、可复核地整理技术型知识库中多篇笔记的 frontmatter。核心不是“把文本替换掉”，而是先建立语义清单，再只在授权范围内修改，并证明正文和无关元数据未被改动。

## 适用范围与语言

按内容和任务目的判断是否适用，不要只看目录名：

- **适用**：软件开发、架构设计、API/SDK、数据库、云平台、DevOps/SRE、网络、安全、数据工程、机器学习、硬件、性能测试、故障排查、ADR、runbook、实验记录、项目文档和技术课程笔记。
- **不适用**：个人随笔、生活日记、游记、情绪记录、文学摘录、非技术读后感，以及与 Markdown frontmatter 无关的普通配置或媒体元数据。
- 事故日志、调试日志和实验日志属于技术内容；名为 `notes` 或 `journal` 的目录不自动代表适用或不适用。
- 论文笔记若只是执行通用字段的精确映射，可以使用本技能；涉及论文原文链接、论文专属标签体系或分析结构时，路由到 `paper-research`。

所有面向用户的计划、澄清问题、变更摘要、异常说明和最终报告默认使用简体中文。路径、命令、代码、YAML 键名及用户已有属性值保持原文；除非用户明确要求，不要为了“中文化”翻译技术标识符或元数据值。

## 完成标准

一次任务只有同时满足以下条件才算完成：

- 只处理用户指定或可明确推断的文件范围。
- 只执行用户授权的检查或变更；“看看、检查、统计”不授权写入。
- 修改后 frontmatter 可被 YAML 解析，已授权触及的字段类型符合目标约定；未授权字段的既有异常只报告。
- 旧值到新值的语义映射符合计划，合并后没有意外重复。
- 除非用户另行授权，正文、文件名、换行风格、BOM 和无关字段保持不变。
- 无 frontmatter、边界损坏、重复键或无法安全解析的文件被单独报告，不悄悄猜测。

## 任务路由与授权

| 用户意图 | 默认动作 |
|---|---|
| 检查、统计、列出问题 | 只读盘点并报告，不修改文件 |
| 给出明确范围和旧值 → 新值映射 | 盘点影响后直接执行，无需重复确认 |
| 要求“整理得更合理”但未给目标体系 | 先盘点并提出映射方案；等待用户确认主观分类或破坏性合并 |
| 删除字段、合并多个值、从文件名推导日期 | 若规则和范围明确则执行；否则只询问会改变结果的那一个关键问题 |
| 修改正文 `#tag`、正文标题、文件名或维基链接 | 说明超出默认范围；得到明确授权后才扩展范围 |
| 论文专属链接、`paper/xxx`、论文结构归档 | 交给 `paper-research`；技术论文的通用字段精确映射仍可由本技能处理 |
| 随笔、个人日记、游记、文学摘录等非技术内容 | 不使用本技能；不要仅因存在 frontmatter 就扩大触发范围 |

不要把“用户可能想要”当作授权。用户已给出明确规则时也不要为了形式再次确认。

## 工作流

### 1. 固定范围与不变量

1. 读取当前目录适用的项目说明，检查工作树状态；保留用户已有的无关修改。
2. 明确根目录、包含规则、排除目录、是否遵循忽略文件，以及是否处理隐藏文件或符号链接。
3. 默认不跟随符号链接，不越过用户给定根目录，也不新增报告文件。
4. 记录本次允许改变的字段和必须保持不变的内容。默认不改正文、文件名及未点名字段。

范围明确时直接继续；只有缺失信息会导致处理另一批文件或产生不同目标状态时才提问。

### 2. 发现文件并识别 frontmatter

优先使用 `rg --files -g '*.md' <scope>` 发现候选文件；`rg` 不可用时再用 `find` 或环境提供的文件枚举工具。说明发现规则，因为忽略文件、隐藏文件和符号链接会改变文件集合。

按以下边界识别 frontmatter：

1. 除可选 UTF-8 BOM 外，文件第一行必须是独占一行的 `---`。
2. 对 Obsidian 笔记，后续第一个独占一行的 `---` 是结束标记。`...` 虽是 YAML 文档结束指示符，但不是默认的 Obsidian frontmatter 边界，应记为非标准/边界损坏；处理其他 Markdown 方言时，只有其规范或实际解析器明确支持才接受 `...`。
3. 没有开始标记时记为“无 frontmatter”；有开始标记但没有结束标记时记为“边界损坏”。后者不能把整篇正文当作 YAML。
4. 没有文件开头的开始标记时，正文中的水平线 `---` 不会开启 frontmatter；已有开始标记时，第一个独占行 `---` 按语法就是结束标记，不能再凭内容猜测作者原意。
5. 记录原始换行符、BOM、结束标记和 frontmatter 原文，供修改后比对。

小规模可直接读取；文件很多时先用一次扫描生成内存清单或临时清单，再按批处理，避免反复打开所有文件。

### 3. 建立语义清单

在把 YAML 加载成映射前，先用启用 duplicate-key rejection 的解析模式或 YAML token/event 级扫描检测重复顶层键。普通 `safe_load` 可能静默保留最后一个值，加载后已经无法证明原文没有重复键。

再用可用的 YAML 解析器读取 frontmatter。注意解析后用普通序列化器写回，可能改变字段顺序、引号，以及日期或布尔值的表示。解析用于理解和校验；若不能往返保留格式，不要用它重写整个文件。

清单至少记录：

- 文件路径、frontmatter 状态和解析结果。
- 目标字段的原始形态与语义值，例如标量、块列表、内联列表、空值。
- 每个唯一值的文件数和出现次数。
- 重复列表项、重复键、类型不一致、大小写或 Unicode 变体。
- `title`/`aliases` 冲突、缺失字段及无法安全判断的异常。

在 Obsidian 中，`tags`、`aliases`、`cssclasses` 都是列表属性；块列表和内联列表只是两种 YAML 表示，标量应记为类型异常。旧字段名 `tag`、`alias`、`cssclass` 已弃用，应作为迁移候选报告，但只有任务授权属性名迁移时才修改。

按字段 schema 判断值是否合法，不要把一条规则套给所有列表。普通自定义列表可以包含数字；Obsidian tag 名只能使用字母、数字、下划线、连字符、用于层级的 `/` 与其支持的常见 Unicode 字符，不能含空格且至少包含一个非数字字符。Obsidian 对 tag 大小写不敏感：`Foo` 与 `foo` 是同一语义值，去重时保留首次出现的拼写；选择全库展示大小写属于单独的规范化决策。明显非法的 tag 先报告，除非映射规则明确，否则不猜测修复。

`aliases` 是当前笔记的替代名称，不是“指向另一篇笔记的链接”。重复 alias 本身合法，但链接自动补全可能出现多个候选；应提示潜在候选冲突，而不是判定元数据无效。已有的显式 `[[目标|alias]]` 链接仍指向写明的目标。不能用“目标文件不存在”来判断 alias 是否孤立。

标题与文件名不同、两篇笔记标题相同都只是候选问题，不自动证明标题错误或文件重复。日期也不得凭内容猜测；只有用户指定来源，或文件名模式明确且日期真实有效时，才可补全。

### 4. 生成变更计划

对每个目标字段构建可复核计划：

```text
字段: tags
操作: rename | merge | add | remove | normalize
映射: 旧语义值 -> 新语义值
影响: 文件数 / 出现次数
格式: 保留原样 | 必要转换 | 统一格式
例外: 无效 YAML、重复键、无法判定项
```

区分“值出现次数”和“受影响文件数”，不要混用。合并或删除前列出碰撞和去重结果。若删除列表最后一项，遵循用户或库内既有约定；无法推断是删除字段还是保留空列表时再询问。

用户提供精确映射时，简要告知影响范围后直接应用。只有标签分类、语言选择、层级设计等目标本身仍是主观决策时，才先展示方案等待确认。

### 5. 执行最小修改

- 精确重命名单个值时，使用限定在 frontmatter 区块内的局部 patch。
- 多格式混用、字段增删或列表合并时，先修改语义值，再按该文件原有块列表或内联列表风格渲染。自定义字段保留原始标量/列表形态，除非目标 schema 另有规定。
- 触及 `tags`、`aliases` 或 `cssclasses` 时，最终值应是 YAML 列表；把旧标量改为列表属于必要格式修复，应计入报告。未授权触及的异常字段只报告，不顺手改写。
- 合并列表后稳定去重，默认保留首次出现顺序；tag 使用大小写不敏感的比较键，其他字段按其 schema 比较。仅在用户要求时排序。
- 不自动改变标签大小写、语言、前导 `#` 或层级 `/` 语义。
- 不自动修复重复键。重复键的有效值取决于解析器，先隔离并报告，除非用户明确给出保留规则。
- 若手工输出 YAML，对空字符串、前后空格、可能被解析成布尔/数字/日期的字符串，以及含 YAML 指示语法的值使用合适引号并正确转义；随后必须重新解析验证。不要把“含任意特殊字符”简单等同于“必须加引号”。
- 复杂改动可以重建 frontmatter 区块，但不得借此序列化或重排未授权字段。

批量转换应保持幂等：对已整理结果再运行一次，不应产生新的差异。

### 6. 分层校验

不要只用全文件字符串搜索证明成功。至少完成以下检查：

1. **结构校验**：重新提取每个已改 frontmatter，以严格模式复查重复键，再做 YAML 解析；若环境没有相应解析能力，明确写出未验证项，不要宣称 YAML 或键唯一性有效。
2. **语义校验**：在解析后的目标字段中核对旧值、新值、去重结果和字段类型。正文中仍出现旧词不算失败。
3. **正文不变量**：比较修改前后结束标记之后的字节或哈希，证明正文未变。
4. **范围校验**：确认变更文件都在目标集合内，且没有意外新增、删除或重命名文件。
5. **差异校验**：查看相对于任务开始状态的完整 diff；在 Git 仓库中针对本次文件运行 `git diff --check -- <changed-paths>`，并确认无关字段和用户原有修改未被覆盖。
6. **幂等校验**：重新计算同一转换；预期变更数应为 0。

任何检查失败都先修复，再汇报完成。无法验证的项目应单列为未知，而不是按通过处理。

### 7. 汇报结果

先给结果，再给证据和例外。小任务用简短列表；目录或操作类型较多时再使用表格。至少包含：

- 使用简体中文陈述结论、证据和未验证项；路径、字段名、命令和属性值按原文引用。
- 扫描、符合条件、修改、未变化、跳过的文件数。
- 实际执行的映射或字段操作。
- 唯一值和出现次数的前后变化；分母为 0 时不计算百分比。
- 结构、语义、正文、范围、diff、幂等校验各自的通过/失败/未验证状态。
- 无 frontmatter、边界损坏、重复键和其他需要用户决定的文件。

## 常见异常及处理

| 异常 | 处理 |
|---|---|
| 无 frontmatter | 只记录；用户明确要求时才新增模板 |
| 开始标记后无结束标记 | 停止自动修改该文件，报告边界损坏 |
| YAML 解析失败 | 保留原文并报告位置；只修复明确授权且无歧义的语法问题 |
| 同一顶层键重复 | 不依赖解析器“最后一个生效”的行为，交由用户或明确规则裁决 |
| 值不符合字段 schema | 按具体字段报告；数字在自定义列表中不一定是错误，tag 则需满足 Obsidian tag 规则 |
| `tag`、`alias`、`cssclass` 旧字段 | 作为迁移候选报告；仅在授权后改为复数默认字段 |
| alias 在多篇笔记中重复 | 标注为合法但可能产生多个自动补全候选，不称为无效或“孤立链接” |
| 正文有同名 `#tag` | 默认保持；需要迁移时单独确认正文范围和去重规则 |
| 文件名或链接需要调整 | 警告可能破坏维基链接，得到授权后另行处理 |
| 大规模笔记库 | 先机器化盘点，再分批应用同一幂等规则；每批校验后继续 |

## 代表性决策示例

**明确映射**：用户说“把后端项目笔记里的 `TODO` 和 `待办` 都合并成 `status/todo`，只改 `Projects/backend/`”。直接盘点碰撞、执行、去重并验证，不再询问是否确认。

**主观分类**：用户说“把架构、数据库和运维笔记的标签整理成合理层级”。先列出现有标签及频次，提出完整旧值 → 新值映射；语言与层级未确定前不写文件。

**只读审计**：用户说“看看 API 文档和 runbook 的 aliases 有哪些问题”。使用中文报告重复 alias、类型异常和解析失败，不修改、不把 alias 当链接检查文件是否存在。
