# 笔记更新指南

执行 `update` 模式时使用本文档。确保修改笔记是一个透明的、有记录的过程，而不是静默覆盖数据。

## 1. 理解更新记录

每个由本 skill 创建或修改的笔记都应在底部维护一个专用的历史记录章节。更新已有笔记时：
1. **绝不静默覆盖**主体中的已有内容，除非它包含事实错误（即使如此也要标记）。
2. 在**理解更新记录**章节中追加新的带时间戳的日志。

### 元数据更新例外

只整理 `tags` 或其他 Frontmatter 属性时，不改变论文事实、用户理解或正文结构，因此：

- 只修改 Frontmatter，不改正文。
- 如果旧文件含 `aliases`，直接删除整个字段及其列表值，不迁移到正文。
- 不追加“理解更新记录”，避免用元数据维护记录污染知识内容。
- 在任务交付摘要中报告映射、受影响文件数和验证结果。
- 如果标签调整依赖了新的论文事实判断，并同步改变正文理解，则仍按下方格式记录该事实更新。

### 更新日志格式
注册更新时使用以下固定模板：

```markdown
### [YYYY-MM-DD] 更新

- **原理解**：用户/AI 此前的理解。
- **新理解**：更新后的观点或事实。
- **修改原因**：变更的上下文或动机（如"组会讨论""测试中发现模型失败"）。
- **证据**：引用的论文章节、代码文件或实验指标。
- **状态**：必须从标准状态中选择（见下方）。
```

---

## 2. 更新状态

为追踪笔记内容的确定性和验证阶段，为每次更新分配以下状态之一：

| 状态键 | 中文名 | 定义 |
| --- | --- | --- |
| `confirmed` | 已确认 | 经论文正文、官方代码库或验证的数学推导明确证实的事实。 |
| `user-understanding` | 用户理解 | 用户对概念的个人直觉或主观重构。 |
| `hypothesis` | 待验证假设 | 需要后续阅读、讨论或编码验证的想法或假设。 |
| `uncertain` | 不确定 | 存在矛盾证据，或细节不可得/未确认。 |
| `deprecated` | 已废弃 | 已被证明错误的概念或先前理解。 |

## 3. 笔记状态管理规则

- 当状态设为 `confirmed` 或 `user-understanding` 时，考虑是否调整笔记 Frontmatter 中的 `status`：
  - 如果完成了初次深度理解，可将 `status` 变更为 `understood`。
  - 如果需要经常复习或进入主动回忆复习期，可将其设为 `reviewing`。
- 更新复杂的结构性章节（如方法流程）时，保持清晰的变更日志，便于用户追踪改动内容。
